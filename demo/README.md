# Лабораторна робота №5 — Асинхронна обробка

У цій лабораторній я додав асинхронну обробку для заявок автосервісу.

Коли створюється заявка, система не повинна чекати завершення всіх повільних дій. Тому повідомлення клієнту, отримання ціни запчастин і розрахунок вартості робіт виконуються у фонових потоках.

## Власний executor

У `AsyncConfiguration` увімкнено `@EnableAsync` та створено executor `repairTaskExecutor`.

- базовий розмір пулу — 2;
- максимальний розмір пулу — 2;
- черга може містити 1 задачу;
- назви потоків починаються з `car-service-async-`;
- якщо пул і черга заповнені, задача відхиляється.

Це потрібно, щоб система не створювала необмежену кількість потоків і не перевантажувала сервер.

## Асинхронні операції

У класі `RepairOrderAsyncTasks` є три операції:

1. `sendOrderAcceptedNotification` — надсилає клієнту повідомлення, що заявка прийнята. Це fire-and-forget операція з типом повернення `void`.
2. `requestPartsPrice` — отримує орієнтовну ціну запчастин і повертає `CompletableFuture<BigDecimal>`.
3. `calculateLaborCost` — обчислює орієнтовну вартість робіт і теж повертає `CompletableFuture<BigDecimal>`.

Усі три методи мають `@Async("repairTaskExecutor")`.

## Кошторис ремонту

У `RepairOrderEstimateService` ціна запчастин і вартість робіт запускаються одночасно. Після завершення обох задач результати об'єднуються через `thenCombine`.

Результатом є `RepairEstimateDto` з такими полями:

- ціна запчастин;
- вартість робіт;
- загальна сума;
- статус кошторису.

Якщо обидва виклики успішні, статус має значення `READY`.

## Помилки, тайм-аут і переповнення

Якщо під час розрахунку виникає помилка, використовується `exceptionally`. Замість падіння застосунку повертається кошторис зі статусом `PENDING`.

Для `CompletableFuture` встановлено `orTimeout(3, TimeUnit.SECONDS)`. Також є метод з `get` і власним тайм-аутом. Якщо очікування завершується за тайм-аутом, користувач отримує статус `PENDING`.

Для `void` методу налаштовано `AsyncUncaughtExceptionHandler`. Він записує помилку у лог.

Якщо executor переповнений, `TaskRejectedException` перехоплюється. Для повідомлення метод повертає `false`, а REST-контролер віддає HTTP 429 Too Many Requests. Для кошторису повертається статус `PENDING`.

## REST API

- `GET /api/repair-orders/{id}/estimate` — запускає розрахунок кошторису.
- `GET /api/repair-orders/{id}/notification` — запускає асинхронне повідомлення клієнту.

Якщо повідомлення поставлено в чергу, endpoint повертає HTTP 202 Accepted. Якщо черга переповнена, повертається HTTP 429.

## Тести

У `RepairOrderAsyncIntegrationTest` перевірено:

- executor має задані розміри та правильний префікс потоку;
- два незалежні розрахунки виконуються паралельно;
- результати правильно об'єднуються у кошторис;
- помилка асинхронної задачі повертає `PENDING`;
- очікування має тайм-аут;
- fire-and-forget повертає керування до завершення повільної задачі;
- помилка `void @Async` методу записується через `AsyncUncaughtExceptionHandler`;
- переповнення executor обробляється без HTTP 500.
